## 推荐部署

先采用每次 visit 最多 2 个网页并发、共享池 8 个 CPU 进程，队列容量 128。该配置约 35.03 页/秒；16 进程为 37.04 页/秒，吞吐高约 5.8%，但 worker 数翻倍。实际机器上的负载、请求大小和网络不同，应先灰度监控再调整。24 个 Agent 每次最多并发 2 页意味着最多约 48 个网页处理请求；池队列限制是全局控制，网页并发则是每个 visit 的限制。

共享服务使用 FastAPI/Uvicorn 和 Python 标准库 ProcessPoolExecutor；CPU 排序继续使用现有 rank_bm25，网页并发使用 ThreadPoolExecutor，保持原顺序。传输包含页面正文和分块，带来本机 HTTP/IPC 开销。服务限流满时会等待，超过准入超时返回 503；不静默切回进程内。取消请求后 CPU 任务尚未结束时仍占用容量。health 的 admitted 包含执行中和进程池内等待的任务，并非真实运行进程数。

```bash
bash inference/scripts/start_shared_bm25_pool.sh
export VISIT_PAGE_CONCURRENCY=2
export VISIT_BM25_POOL_URL=http://127.0.0.1:18215
```

环境变量须传给新启动的 QUEST Agent，已有进程不会自动更新。网页并发默认 1，池 URL 默认未设置；共享池用于启用 retrieval_experiment 的选择路径，不自动覆盖其他摘要路径。可用 QUEST_BM25_WORKERS、QUEST_BM25_QUEUE_LIMIT、QUEST_BM25_PORT 配置服务。服务监听本机回环地址；应由进程管理器负责重启和监控。

实际线上评估仍须观察 Jina 限流、页面抓取耗时、内存、CPU、队列及答案正确率；此结果不能推断端到端加速或准确率不变。原始每次访问、指标与源码哈希保存在 benchmark-results.json；真实网页快照保存在同目录，含外部网页内容，应按本地实验数据管理。
